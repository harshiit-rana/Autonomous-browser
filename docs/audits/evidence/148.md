# Evidence for legacy #148 [SWM-02] (worker isolation and lifecycle), delivered by #229 [SWX-03]

Running-app evidence: `scripts/e2e_worker_isolation.mjs` launches the built app (`dist/`, Electron 33.4.11, Chromium 130, Node 20.18.3, Windows x64) with Playwright `_electron` on a throw-away profile and drives the app's own `SwarmManager` / `WorkerHost` modules inside the main process against a local fixture server. Raw output: `docs/audits/evidence/SWX-03/report.json` (result `PASS`). Re-run with `npm run build && npm run rebuild && npm run e2e:workers`.

| Claim | What the run observed (from `report.json`) |
|---|---|
| Dedicated view per worker | 3 workers = exactly 3 new `WebContents` and 3 new child views in the window (baseline 2 and 1). |
| Distinct partitions and sessions | `agent-e2e-iso-iso_1`, `-iso_2`, `-iso_3`; the three `Session` objects are pairwise different, each equals `session.fromPartition(<its partition>)`, none is the default session. `session.getStoragePath()` is `null` for all three because they are in-memory partitions (nothing is written to disk). |
| Cookie / localStorage isolation | Worker 1 set `owner=worker1` on the fixture origin and read it back (`document.cookie = "owner=worker1"`, positive control). Workers 2 and 3 on the same origin printed `document.cookie = ""` and `localStorage.owner = null`, their session cookie jars were empty, and the fixture server logged no `Cookie` header for their requests. Screenshots: `cookie-worker1.png`, `cookie-worker2.png`, `cookie-worker3.png`. |
| Real settle logic | A page that fetches 300 ms after load and renders at about 1000 ms was fully rendered when `navigate()` returned after 1723 ms (the old fixed wait was 600 ms). A page that mutates forever returned at the 10 s deadline with `settled: false, reason: "deadline"`. |
| Guards | `file:`, `chrome:`, `javascript:` and `devtools:` navigations were refused; the page's `geolocation` request failed with code 1 and `Notification.requestPermission()` returned `denied`; `window.open()` returned `null` and no `WebContents` was created; a download was cancelled. Each produced a worker event carrying the worker's name and glyph. |
| Crash | `forcefullyCrashRenderer()` was detected (`render-process-gone`), the worker was recovered by reloading its last URL and then navigated normally. |
| Teardown | After `shutdown()` every worker `WebContents` was confirmed destroyed and the counts returned to the baseline (2 `WebContents`, 1 child view). Closing the parent window with 2 running workers destroyed both workers. |
| 20-worker leak test | 20 workers spawned and torn down (5 batches of 4, each navigating a page): `webContents.getAllWebContents().length` returned to baseline, main-process heap growth after `gc()` was +0.17 MB (limit 20 MB), renderer working set 285468 KB before and 285504 KB after. Whole-process RSS grew 19.1 MB (not asserted; in-memory sessions are never freed by Electron, see `docs/limitations.md`). |
| Real mission | A `/swarm` mission started through the app's IPC reached `completed`; its recorded worker events carry a stable name, colour and glyph (Ada, Bram, Cleo) and no worker `WebContents` survived the mission. The mission's workers navigated to the real `duckduckgo.com`, because `SwarmCoordinator.planMission` supplies no URLs yet (#228). |

What this does not show: the worker views are not visible in the UI (#232), `ResourceGovernor` hibernation is not wired (#231), and macOS / Linux were not run. See `docs/limitations.md`.
